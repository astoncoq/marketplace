01 · PROBLEM STATEMENT

B2B telco is growing into 5G, IoT and Edge —
but the selling model is still manual.

Slow time-to-market
Launching an offer or bundle takes months of legacy BSS changes. 5G / IoT / Edge opportunities reach the market late — or never.
Unmonetized ecosystem
The solutions customers need combine operator services with partner products — but there is no industrial way to onboard, co-sell and settle with those partners.
Opaque B2B buying
Enterprise buyers want to discover, configure and buy online. Today: catalogs in technical jargon, quotes over email, weeks of waiting.
The opportunity: headless commerce on TM Forum Open APIs — one multi-provider catalog, an AI-guided buying experience, and native partner settlement.
REFERENCE CASE · CURRENT STATE

How a tier-1 operator runs this today — without a DBP

A live B2B large-account case with a digital partner (Microsoft-type catalog). The operator deliberately stays out of the middle: the client subscribes and self-manages directly with the partner. Six stages, mostly manual, stitch the relationship together end-to-end.

01 · Partner onboarding
Marketing negotiates PVP price list, categories and discount level per partner. Billable concepts created manually in billing, one per category.
MANUAL NEGOTIATION
02 · Product onboarding / mod.
Partner catalog published on its own site or handed to marketing. Client discount per category loaded by hand into the master catalog repository.
MANUAL LOAD
03 · Fulfillment (A/M/D)
Client subscribes, modifies or cancels directly in the partner's console (or via care, who impersonates the client). No inventory held on the operator side.
API / CONSOLE SSO / EMAIL
04 · Invoicing to client
Partner sends a monthly file with amounts per client/item. Operator applies the agreed discount, injects charges into billing, publishes the client detail file.
SFTP / API FILE
05 · Care / tech post-sale
Care triages telco vs. partner issues, escalates partner incidents, and can impersonate the client inside the partner's console. No proactive monitoring.
TRIAGE + ESCALATION
06 · Settlement
Same billing file doubles as the payout basis, so reconciliation is largely automatic — but disputes, margin analysis and price-list changes are handled by hand.
FILE-BASED RECONCILIATION
No unified inventory, no single console, no orchestration — each handoff is its own file, email or manual task.

REFERENCE CASE · SECOND SCENARIO

Microsoft isn't run like a generic partner — it goes through Infiterra

Two integration models coexist today. Generic digital partners follow the file/email-driven process just covered. Microsoft runs through Infiterra, a CSP management SaaS, which holds a direct API integration with Microsoft Partner Center — a materially more automated path.

Ciebercloud — operator app, AWS Cloud, SSO (SAML/OIDC)
↓ API (OAuth/API key)↓ API (OAuth/API key)

Data sync & provisioning

CSP mgmt, licenses, data retrieval
direct API — data exchange & service mapping
Ciebercloud ↔ Infiterra API handles data sync & provisioning; Ciebercloud ↔ Microsoft API handles CSP management, licenses and data retrieval.
Infiterra ↔ Microsoft Partner Center is a direct API integration of its own — Infiterra is a CSP layer in the middle, not just a file drop.

Two onboarding playbooks. Teams must know which model applies — generic-partner or API/CSP — per partner.
Gap: a one-off CSP integration becomes just another partner application under one governance model.
